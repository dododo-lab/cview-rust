# 성능 5차 — 멀티라이브 주기 작업 정리 (진단 목록 D)

측정일 2026-11-08. 근거는 v0.1.82 실제 사용 디버그 로그(2026-11-06~07, 약 39시간)와 코드 경로 확인이다.

## 진단을 다시 확인한 결과
진단 때는 "같은 채널의 live-status 를 채팅 머리와 패인 폴이 따로 부른다(v3 4,186 + v3.1 2,707건)" 로 보았는데, 경로를 따라가 보니:

- **v3.1**(`/polling/v3.1/.../live-status`)은 시청 이벤트(`live_watch_events.rs`)가 30초마다 `WATCH_CONTINUED` 를 보내기 전에
  `liveTokenList` 를 다시 읽는 호출이다(상태 최대 나이 10초 < 주기 30초 → 이벤트마다 한 번). 웹과 같은 흐름이고 토큰 신선도가
  계정 시청 집계에 걸려 있어 **건드리지 않았다**.
- **채팅 머리 live-status 폴**(`chat/header.rs` `start_live_info_polling`)은 앱에서 시작하는 곳이 없다(재연결 복구에서만 이어 붙음).
- **v3** 채널별 호출 간격: 50~70초 1,694 · 70초 이상 1,859 · **30초 미만 309(7.4%)** · 30~50초 289.
  60초 주기 패인 폴 말고 짧은 간격으로 붙는 것은 메뉴 복귀 직후 1회 조회(`poll_live_status_once`), 재생 오류 때 방송 종료 확인
  (`stream_ended_probe`), 본 플레이어 재연결의 종료 확인이다.

## 바꾼 것
- `ChzzkApiClient::live_status_recent(channel, max_age)`: 채널별 마지막 live-status 응답(30초, `LIVE_STATUS_SHARE_AGE`)을
  주기 폴러가 나눠 쓴다. `live_status`(늘 새로)도 응답을 메모에 남긴다. 메모는 64개를 넘으면 2분 지난 것을 지운다.
- 멀티라이브 패인의 60초 주기 폴만 `live_status_for_poll` → `live_status_recent` 를 쓴다. 방송 종료 확인·메뉴 복귀 조회는 그대로 새로 받는다.
- 멀티라이브 상태 감시 루프(`multilive://state`)는 세션이 없으면 1초 → 30초마다 깬다(세션이 생기면 매니저 변화로 바로 깬다).
  세션 없을 때 주기로 볼 것은 자동 네트워크 프리셋의 불안정 유지(90초)가 끝났는지뿐이다.

## 기대 효과 (로그 기준 어림, 실제 앱 전후 측정은 하지 않음)
- v3 live-status: 다른 호출 뒤 30초 안에 돈 패인 폴이 빠진다 — 최대 약 7%(39시간 309건, 분당 약 0.13건).
- 앱이 놀 때(재생 없음) 멀티라이브 상태 루프 깨움: 초당 1회 → 30초에 1회(상태 DTO 만들기·자동 네트워크 판정 포함).
- 둘 다 작다. 멀티라이브 CPU(3패인 약 36%)의 대부분은 WebKit GPU·WebContent 의 영상 디코드·합성이라 이 정리로는 줄지 않는다.
