# 성능 4차 — 붐비는 채팅에서 줄 지우기 묶기

측정일 2026-11-08. 모의 IPC·헤드리스 Chromium, 채팅 패널 360×860에 합성 메시지를 50ms마다 묶어 4초 동안 흘림(줄 상한 300).
"20ms 넘은 프레임"은 rAF 간격 기준. CPU 감속은 느린 PC(특히 Windows 저사양) 가정.

## 원인
- 4배 감속·초당 200개 CPU 프로파일에서 `chat-follow.js` `snap()`(scrollHeight 읽기)이 4초 중 1.28초 — 실제로는 강제 레이아웃이
  `snap()` 에 몰려 보일 뿐이다. `snap()` 을 꺼도 같은 레이아웃이 프레임 그리기로 옮겨 갈 뿐 총량은 같았다.
- 트레이스: 플러시마다 문서 전체 레이아웃(4배 감속에서 1회 약 20ms). 목록이 상한 아래에서 붙이기만 할 때는 790줄이어도 1회 11.8ms·
  프레임 6.6% 초과였는데, 상한에 닿아 **플러시마다 앞에서 몇 줄씩 지우기 시작하면** 남은 줄 전체가 위로 밀려 다시 배치된다.
- 아니었던 것: 문서 전체 MutationObserver(motion·a11y, 합 10ms 미만), 목록 밖 `hidden` 토글, `contain: strict`·`content-visibility`.

## 바꾼 것
- `chat-follow.js` `trimFront(list, max)`: 상한의 1/4(최소 20줄)을 더 넘칠 때까지 두었다가 상한까지 한 번에(Range) 지운다.
  본 채팅(`chat.js`), 멀티채팅 통합 목록(`multichat.js`, 600줄), 멀티라이브 통합·칸 채팅(`ml-multichat.js`)에 적용.
  목록은 순간적으로 상한의 최대 125%까지 들고 있다(300줄 → 최대 375줄).
- Rust: 추가 채팅 세션 이벤트(`chat://session-event`)를 `json!` 으로 Value 트리에 한 번 더 복사하던 것을 빌린 구조체로 바로 직렬화.

## 전후 (main 82c0af9 ↔ 이 브랜치)
| 조건 | 20ms 넘은 프레임 전 → 후 | 레이아웃 합 전 → 후 |
|---|---|---|
| 1배, 초당 200 | 0% → 0~0.4% | — |
| 1배, 초당 800 | 0% → 0% (3회) | 488 → 328ms (3회 평균) |
| 4배, 초당 50 | 0% → 0.4% | — |
| 4배, 초당 200 | **25~59% → 3.5~10.8%** | 1,100 → 475ms |

실제 사용 로그(2026-11-06~07)의 채팅은 평균 초당 0.9개, p95 3.4개, 최대 30개 — 보통의 단일 채팅에서는 체감 차이가 작고,
멀티채팅·멀티라이브 통합 채팅처럼 여러 채널이 합쳐지는 목록과 느린 PC 에서 효과가 크다.
4배 감속 초당 800개는 줄 넣기 자체(플러시마다 40줄)가 한계라 그대로다.

회귀 검사: `tools/ui-regression/perf.mjs` P04 — 4배 감속 초당 200개에서 앞에서 지운 횟수 ≤ 15, 한 번에 ≥ 20줄,
줄 수가 상한~125% 안, 20ms 넘은 프레임 < 15%. 고치기 전 코드에서는 "앞에서 지운 횟수 48" 로 실패한다.
