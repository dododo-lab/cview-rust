# 썸네일 캐시 — 전후 측정 (2026-10-21)

사용자 요청: "앱에서 표시되는 모든 썸네일이 빠르게 표시될 수 있도록(데이터베이스화 등)".
커밋: `0e71cc3`(디스크 캐시) · `b27348e`(서비스·`cvimg:` 프로토콜) · `778c0fb`(화면 36곳·크기 단계·설정).

## 바꾸기 전 — 무엇이 느렸나
- 모든 `<img>`(20개 파일 36곳)가 치지직·네이버 CDN 을 직접 불렀다. 캐시는 웹뷰 HTTP 캐시뿐.
- **라이브 썸네일은 CDN 이 `Cache-Control: max-age=5`, ETag·Last-Modified 없음** — 5초가 지나면 웹뷰가 통째로 다시 받는다.
  그래서 같은 화면도 다시 실행하면 처음과 거의 같은 시간이 걸렸다(조건부 요청도 불가).
- **크기가 칸보다 훨씬 컸다**(실측):

  | 그림 | 받던 것 | 칸(물리 픽셀) | 바꾼 것 |
  |---|---|---|---|
  | 라이브 썸네일 | `image_720` = 1280×720, 152KB | 약 658×370 | `image_405` = 720×405, **60KB(−61%)** |
  | 아바타(네이버 이미지) | 원본 320~1920px PNG, 최대 170KB | 약 64~68 | `?type=f120_120_na` 120×120, **24KB(−86%)** |
  | 채널 화면 큰 아바타 | 원본 | 약 192 | `f240_240_na` |

  (`image_N` 의 N 은 세로 픽셀이고, 서버가 허용하는 값만 된다 — `thumbnail_tier.rs` 화이트리스트.)

## 바꾼 것
- **디스크 캐시**(`cview-persistence::image_cache`): `image-cache/index.sqlite`(URL SHA-256 키·종류·형식·ETag·크기·받은 시각·마지막 사용) + `blobs/`.
  상한 256MB, 넘으면 오래 안 쓴 것부터 90% 까지. 쿠키·토큰은 담지 않는다.
- **서비스**(`image_service`): 메모리 48MB → 디스크 → 네트워크. **오래된 것도 바로 내주고 뒤에서 새로 받는다**
  (라이브 45초, 아바타·포스터·그 밖 7일). 같은 URL 은 한 번만, 동시 16개, 이미지 전용 연결. 허용한 https 이미지 CDN 만.
  오프라인이면 캐시된 것을 내준다.
- **`cvimg:` 프로토콜**: 화면은 `imageSrc(url, 종류)` 로 `cvimg://localhost/<종류>%2F<URL>`(Windows `http://cvimg.localhost/...`)을 부른다.
- 설정 → 고급 → 성능·진단: 썸네일 캐시 크기·개수 표시, "썸네일 캐시 비우기".

## 측정 방법
- 시험 빌드는 **다른 번들 ID**(`app.cview.rust.test`)로 — 실행 중인 배포 앱·키체인·데이터와 떨어져 있다.
  사용자 화면을 방해하지 않게 **숨겨 실행**(`open -g -j`).
- 숨긴 창은 타이머가 1초 단위로 묶이고 그리기가 멈춰 "화면에 보이기까지" 는 잴 수 없다(첫 시도 숫자가 1초 계단으로 나와 버렸다).
  그래서 **그리기와 상관없는 값**을 쟀다: 첫 화면에 없는 인기 라이브 51~62번의 썸네일 12장 + 아바타 12장을
  `new Image().decode()` 로 한꺼번에 불러 모두 끝날 때까지(Promise 완료 시각은 숨김 영향을 받지 않는다).
  전 = 원본 URL 직접, 후 = 앱의 `imageSrc`(캐시 + 크기 단계).
- 도구: `perf/tools/thumbs2.js`, `thumbcmp2.sh`, `thumbone.sh`, `thumbft.sh`.

## 결과 (24장)
| 상황 | 전 | 후 |
|---|---:|---:|
| **다시 실행(캐시 있음)** — 모두 끝 | 466 · 513ms | **8 · 8ms** |
| 처음(캐시 없음) — 모두 끝 | 665 · 686 · 533ms (중앙 665) | **508 · 453 · 431ms (중앙 453, −32%)** |
| 처음 — 한 장 p50 | 224 · 403 · 229ms | 308 · 257 · 252ms |
| 같은 실행 안에서 다시 | 0~6ms | 0~1ms |
| 받는 양(장당) | 썸네일 152KB · 아바타 ~170KB | 60KB · 24KB |

- 다시 실행 때 썸네일이 **바로**(디스크·메모리에서 8ms) 나온다 — 가장 큰 차이.
- 첫 실행은 한 장씩은 비슷하고(Rust 를 한 번 거치는 비용 ≈ 작은 그림으로 줄인 시간), 전체가 끝나는 시각은 32% 빠르다.
- 처음 만든 판은 첫 실행이 오히려 느렸다(1404ms): 이미지 CDN 이 HTTP/1.1 이라 동시 6개가 곧 연결 6개였고,
  디스크 쓰기를 기다린 뒤 응답했다. 동시 16개·이미지 전용 연결·디스크 쓰기는 응답 뒤로 바꿔 고쳤다.

## 하지 않은 것
- 캐시 상한은 256MB 고정(설정에서 바꾸기는 아직 없음).
- 다음 줄 미리 받기는 넣지 않았다 — 목록 이미지는 `loading="lazy"` 이고, 다시 볼 때는 캐시가 즉시 답한다.
- HTTP/2 는 켜지 않았다 — reqwest 의 `http2` 기능은 작업공간 전체(API 클라이언트 포함)에 적용돼 범위가 커진다.
