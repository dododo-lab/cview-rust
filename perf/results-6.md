# 성능 6차 — 작은 정리 (진단 목록 E)

측정일 2026-11-08.

## 창을 끄는 동안 메인 스레드에서 동기 디스크 쓰기
- 창 이동·크기 조절 이벤트(`WindowEvent::Moved/Resized`)마다 `window-frame.json` 을 원자 쓰기(임시 파일 + `sync_all` + rename) 했다.
  macOS 에서 Rust `sync_all` 은 `F_FULLFSYNC` 라, 같은 디스크(`~/Library`)에서 한 번에 **중앙값 5.0ms · p95 5.2ms · 최대 15ms**(60회).
- 창 이벤트 처리는 메인 스레드에서 돈다. 끄는 동안 이벤트가 초당 수십 번 오므로 그만큼 메인 스레드(웹뷰 그리기·입력)가 막혔다.
- 바꾼 것: `window_prefs::FrameSaver` — 이벤트 자리에서는 값만 적고, 마지막 이벤트 뒤 0.5초 조용하면 백그라운드 스레드에서
  한 번 쓴다(같은 값이면 건너뜀). 창을 닫을 때(`CloseRequested`)와 앱이 끝날 때(`RunEvent::Exit`, ⌘Q)는 기다리지 않고 바로 쓴다.
- 효과(계산): 끄는 동안 메인 스레드 디스크 쓰기 이벤트당 약 5ms → 0, 쓰기 횟수 초당 수십 번 → 끈 뒤 1번.

## 살펴보고 하지 않은 것
- 이미지 캐시(`image_service.rs`): 메모리 캐시 조회의 O(n) 순서 갱신은 항목 약 1,600개(48MB/약 30KB)에서 한 번에 약 10µs 수준이고,
  응답 바이트 복사는 Tauri 응답이 소유 버퍼를 요구해 피할 수 없다. 디스크 쓰기(`last_access` UPDATE·`SUM(size)`)는 메모리 캐시를
  놓쳤을 때와 새로 넣을 때만 일어난다. 바꿀 만한 이득이 없다.
- 시작 IPC 중복(`settings_get` 4회·`auth_status` 2회·`insights_overview` 2회): 한 번에 1ms 안쪽이고 조작 가능 시점을 정하는
  경로(홈 데이터·첫 화면 그림)에 있지 않다. 공유하려면 받은 설정 객체를 모듈끼리 나눠 고쳐 쓰는 위험이 생겨 두었다.
