# 성능 3차 — 진단(v0.1.82)과 팔로잉 시작·폴링 개선

측정일 2026-11-08. 실제 앱 수치는 디버그 로그(`~/Library/Application Support/app.cview.rust/logs/debug.jsonl`)를
`perf/tools/analyze-log.py` 와 아래 스크립트로 읽었다. UI 수치는 `perf/tools/ui/measure-ui.mjs`(모의 IPC, 헤드리스 Chromium).

## 1. 진단 기준선 (v0.1.82, 코드 변경 전)

실제 사용 로그 2026-11-06~07(약 39시간, 8.7만 줄):

| 항목 | 값 |
|---|---|
| 페이지 로드 → 조작 가능 | 3.4 · 4.9 · 5.2 · 4.9초 (모의 IPC 에서는 0.4초) |
| 프로세스 시작 → setup 끝 | 0.27~0.91초 |
| API 요청 | 33,359건 중 `channels/followings` 18,448건(56%), 548MB(하루 약 340MB) — 61초마다 8페이지 |
| live-status 폴 | v3 4,186건 + v3.1 2,707건(같은 채널 이중 폴 의심) |
| CPU(앱+WebKit 합, 중앙값) | 재생 없음 1.5% · 창 숨김+360p 1개 19.6% · 멀티 3개 35.8% · 720p↑ 2개 포함 51% |
| RSS | 재생 없음 0.86GB ~ 멀티라이브 1.5GB |

시작이 느린 까닭: 홈은 팔로잉 결과를 기다리는데, 팔로잉 폴은 목록 8페이지 + 라이브 상세 24건을 모두 마쳐야 끝났다.
API 요청 게이트(`gate.rs`, 기본 초당 10회)가 이를 100ms 간격으로 줄 세워 약 3.2초. 끝난 직후 화면 진입이 상세 상한(24)
때문에 남은 채널을 채우려고 팔로잉 목록 8페이지를 한 번 더 받았다.

모의 IPC(1배 / CPU 4배 감속):

| 항목 | 1배 | 4배 |
|---|---:|---:|
| DOMContentLoaded ms | 96 | 421 |
| 시작 스크립트 ms | 35 | 156 |
| 시작 JS | 68개 916KB(전부 즉시) | |
| 시작 IPC | 23회(settings_get 4·auth_status 2·insights_overview 2) | |
| 화면 전환 ms | 9~30 | 34~104 |
| 채팅 폭주 프레임 >20ms | 50/s 0% · 200/s 0% · 800/s 1.7% | 50/s 0% · 200/s 47% · 800/s 53% |

4배 감속 채팅 폭주의 CPU 프로파일: `chat-follow.js` `snap()` 의 `scrollHeight` 강제 레이아웃이 4초 중 1.28초.
문서 전체 MutationObserver(motion·a11y)는 합 10ms 미만이라 원인이 아니고, `content-visibility`/`contain` 만으로는 줄지 않았다.

## 2. 이번 변경 — 팔로잉 시작 대기·폴링

- A: 화면 진입은 목록을 받는 즉시 결과를 받는다(상세는 뒤에서). 상세 상한 때문에 남은 채널은 목록 없이 상세만 보충.
- B: 팔로잉 목록을 size=505 로 받아 끝(다음 페이지가 빔)이 확인되면 그대로 쓴다. 아니면 기존 50개씩 나눠 받기.

같은 Mac·같은 계정(팔로잉 약 330채널, 라이브 약 48채널), 서명 없는 테스트 빌드. 첫 두 실행은 서명이 바뀐 빌드라
키체인 허용 창에서 로그인 복원이 약 5초 멈춰 시작 시간에서 뺐다.

| 항목 | 전(v0.1.82 로그) | 후(테스트 빌드) |
|---|---|---|
| 프로세스 시작 → 팔로잉 결과(prefetch_following) | 3.3 · 3.7 · 3.8 · 4.7초 | **0.72 · 0.72초** |
| 페이지 로드 → 조작 가능 | 3.4 · 4.9 · 4.9 · 5.2초 | **2.2 · 0.6초**(두 번째는 썸네일 캐시) |
| 폴마다 팔로잉 요청 | 8~9회(약 270KB) | **2회**(237KB + 빈 페이지 89B) |
| 시작 직후 팔로잉 목록 중복 받기 | 있음(8페이지) | 없음 — 상세만 보충 |
| 상세(live-detail) | 홈이 24건을 기다림 | 뒤에서 55건(상한 24 + 보충), 홈이 썸네일을 이어 채움 |

남은 시작 시간은 홈 첫 화면 썸네일 대기(최대 1.5초, `STARTUP_IMAGES_MAX_MS`)가 대부분이다.
받는 바이트는 거의 같다 — 치지직 API 가 응답을 압축하지 않는다(gzip·br·zstd 요청 모두 같은 크기).
바이트까지 줄이려면 라이브 전용 경로(`/service/v1/channels/followings/live`, 인증 필요 — 401 확인)를 검증해야 한다.

## 다음 단계 후보 (진단 우선순위)

1. 채팅 폭주: `snap()` 강제 레이아웃, Rust 채팅 이벤트 묶음·대상 창 지정, 결과를 안 쓰는 채팅 VM 계산.
2. 멀티라이브 중복 폴링: live-status v3/v3.1 이중 폴, 1초 상태 루프 상시, 패인별 HTTP 클라이언트.
3. 작은 정리: 시작 IPC 중복, 이미지 캐시(O(n) 조회·응답 복사·디스크 적중마다 쓰기), 창 이동마다 동기 fsync.
