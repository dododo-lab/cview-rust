# CView 프레임 보간(VFI) 개발 계획 — 1080p60 라이브·macOS+Windows (시나리오 B)

- 작성: 2026-11-22. 기준 v0.2.11(`6e537d1`). 앱 코드·앱 빌드·배포는 바꾸지 않았다.
- 출발점: AI·macOS Neural Engine 실시간 VFI 연구 보고서(`docs/research/ai-neural-engine-vfi-research.md`, 2026-11-22, 로컬 문서이며 저장소에는 없음)의 7.2절 '시나리오 B'와, 저장소의 [뉴럴엔진 보간 연구·검증 보고서](frame-interpolation.md)(#99).
- 측정 기기: MacBook Pro 16형(2021) M1 Max(CPU 8+2, GPU 32코어, ANE 16코어), 64GB, macOS 27.3, Xcode 27.2, 전원 연결.
- 측정 환경: CView 라이브 재생을 포함해 다른 앱이 함께 실행 중이었다(시스템 CPU 약 35%, GPU 약 21%, Vitals). 아래 수치는 이 실사용 부하에서 잰 값이다. 측정 도구는 모두 명령줄 도구이며 창을 띄우지 않는다.
- 도구: [`tools/frame-interp-lab`](../../tools/frame-interp-lab/README.md)의 `bench.m`(보호 장치·실시간 모사·`--algo rife` 추가), `rife-graph.h`, `rife-mpsgraph.m`, `rife-export.py`, `mps-ops-micro.m`, `mpp-conv-micro.m`, `run-plan.sh`. 원시 로그: [`vfi-dev-plan-2026-11-22/raw`](vfi-dev-plan-2026-11-22/raw/).

## 1. 요약

**앱 통합 보류를 유지한다.** 이 Mac에는 1080p 60→120을 실시간 목표(보간 1장 p95 ≤ 12ms) 안에 처리하는 경로가 없다. 보호 장치와 서킷브레이커는 쓸모가 확인됐지만 글자 보호 기준을 모든 조건에서 넘지는 못했다.

3단계(학습 가중치, 4.6절)도 진행했다. **화질은 RIFE 4.25가 VT보다 분명히 좋다.** 1080p 30→60에서 전체 +2.3dB, 채팅 +5.6dB, 자막 +3.3dB이고, 정지 보호를 더하면 글자 기준(C4)을 통과한다. 하지만 같은 화질을 내는 설정(scale 1, FP32)은 이 Mac GPU에서 1080p 44.7ms라 시간 기준(C1)을 넘지 못한다. 빠른 설정(lite, scale 0.5)은 자막이 크게 무너진다.

| --- | --- | --- |

새로 알게 된 사실:

1. **1080p RIFE의 GPU 시간은 합성곱 계산량이 아니라 보조 연산이 정한다.** MPSGraph에서 전치 합성곱(블록 4: 8.4ms, 0.8 TFLOPS)과 전체 해상도 concat(4.5ms)이 느리다. 전체 해상도 채널 slice는 단독 70ms까지 나온다. 가중치를 재배열하면 같은 값을 내는 구성(위상 분해 합성곱, 출력 분리, 워핑 합치기)으로 바꾸자 79ms에서 40ms로 줄었다.
2. **FP16은 쓰면 안 되고, 이 GPU에서는 FP32 비용이 작다.** 학습 가중치로 재 보니 FP16 출력이 FP32 기준과 최대 2e-2(scale 1)~0.6(scale 0.5) 벌어졌다. 워핑만 FP32로 해도 줄지 않아, 연구 보고서가 경고한 흐름 누적 오차가 합성곱 쪽에서 생긴다. 시간 차이는 7% 안팎이다(1080p p50 40.0 / 43.0ms).
3. **ANE는 쉬는 동안 느려진다.** 다른 프로세스가 ANE를 계속 쓰는 동안 720p 보간은 오히려 빨라졌다(p50 9.6 → 8.1ms, 제때 보간 99.0% → 100%). 브레이커로 쉬었다가 다시 시도한 첫 요청은 0.16~1.1초 걸렸다. 재시도 직후 결과로 다시 차단하면 안 된다.
4. **VT 보간은 천천히 스크롤되는 반투명 채팅을 60→120에서 크게 망친다**(채팅 영역 20.8dB, 그대로 두기 31.3dB). 1080p60 → 120Hz가 CView의 실제 목표이므로, 처리 시간이 해결돼도 이 화질 문제는 남는다.
5. **실시간 측정 스레드는 시간 제약(실시간) 정책이어야 한다.** 일반 스레드는 `mach_wait_until`이 평균 4.5ms 늦게 깨어나, 720p 60→120의 제때 보간 비율을 57%로 잘못 보이게 했다(정책 적용 뒤 99.0~99.1%). 앱의 표시·보간 스레드 설계에도 그대로 해당한다.
6. **MPSGraph에 값이 틀리는 경우가 있다.** depthToSpace 두 번(TF 순서 → PixelShuffle 순서) 뒤에 확대 없이 바로 더하기가 붙으면 왼쪽 가장자리 값이 틀렸다(최대 차 0.56). 사이에 `identity`를 끼우면 맞는다. 학습 가중치와 CPU 기준 구현이 없었다면 찾지 못했을 오류다. 4단계에서 그래프를 바꿀 때마다 정합 검사(`rife-mpsgraph --check`)를 다시 돌려야 한다.
7. **RIFE는 VT보다 글자를 덜 망친다. 경량 설정은 반대다.** 같은 장면에서 RIFE 4.25 자막은 VT보다 +3.3~+8.1dB 높다. 4.25.lite와 scale 0.5는 흐름을 더 거친 해상도에서 시작해 가는 글자를 놓친다(1080p 자막 23.1·18.5dB). 1080p에서 시간을 줄이려고 해상도·채널을 깎는 방법은 쓸 수 없고, 하드웨어가 빨라져야 한다.

다음 권고(우선순위 순):

1. **2단계(기기 재측정)를 먼저 한다.** M4 Pro·M5급 기기에서 `run.sh`와 `run-plan.sh`(가중치가 있으면 `rifeq` 절 포함)를 그대로 돌린다. 이제 기준이 분명하다. **RIFE 4.25 scale 1 FP32를 1080p에서 25ms(30→60) 또는 12ms(60→120) 안에** 돌릴 수 있는지 본다. 이 Mac의 1.8배·3.7배 속도가 필요하다.
2. 3단계 남은 일: 타이머(바뀌는 숫자)와 60→120 반투명 채팅. 블록 매칭 conf 대신 **RIFE가 내는 흐름·마스크와 두 워핑 결과의 차이(워핑 잔차)**를 신뢰도로 써서, 그 영역만 그대로 두기로 되돌리는 장치를 시험한다. 실제 방송 표본도 필요하다(합성 장면의 1080p 60→120 채팅 '그대로 두기' 31.3dB는 다른 조건보다 유난히 높아 장면 특성일 수 있다).
3. 4단계는 2단계에서 속도가 확인된 기기에서만 시작한다. MPSGraph 외 경로(Metal 4 MPP·ML 인코더)는 M5 GPU Neural Accelerators가 있어야 의미가 있다.
4. 네이티브 재생 실험 앱(5단계)과 앱 통합(6단계)은 2·3단계 성공 기준을 넘긴 뒤에만 시작한다.

## 2. 시간 예산과 공통 성공 기준

보간 1장의 예산은 `B = 1000 / (출력 fps − 입력 fps)`, 실전 목표는 `p95 ≤ 0.75·B`다(연구 보고서 2.1절). 표시 지연은 `H = T/2 + B`로 둔다(T = 입력 간격). 중간 프레임은 다음 원본이 도착한 뒤 B 안에 준비돼야 한다.

| 변환 | B | p95 목표 | p99 상한 | 추가 표시 지연 |
| --- | ---: | ---: | ---: | ---: |
| 1080p 30→60 | 33.3ms | ≤ 25ms | ≤ 33.3ms | ≤ 50ms |
| 1080p 60→120 (CView 목표) | 16.7ms | ≤ 12ms | ≤ 16.7ms | ≤ 25ms |

모든 단계가 쓰는 기준(앞 번호로 부른다):

- **C1 처리 시간**: 보간 + 보호 장치 + 색 변환 합계가 위 표의 p95·p99 안.
- **C2 실시간 모사**: 30초 이상, 절대 시간표, 비동기 1건 기준으로 제때 보간 ≥ 95%, 버린 보간(마감 초과) ≤ 1%, 보간↔원본 전환 ≤ 분당 60회.
- **C3 움직임 이득**(합성 장면, 정답 대비 휘도 PSNR): 빠른 공 영역 ≥ 그대로 두기 + 6dB. 전체 ≥ max(그대로 두기, 단순 섞기) + 1dB.
- **C4 글자 보호**: 자막·타이머·채팅 영역이 각각 그대로 두기 − 1.0dB 이상. 지금 앱이 보여 주는 것이 '그대로 두기'이므로, 방송 화면에 박힌 글자가 지금보다 눈에 띄게 나빠지지 않아야 한다.
- **C5 장면 전환**: 합성 장면에서 재현율 100%, 오검출 0. 실제 방송 표본에서 재현율 ≥ 95%, 정상 쌍 오검출 ≤ 0.5%. 전환 쌍의 전체 PSNR ≥ 그대로 두기 − 0.5dB.
- **C6 자원**: 추가 CPU ≤ 1코어의 15%. GPU 경로는 GPU 사용 증가 ≤ 20%p. 시스템 전력 증가 ≤ 2W(전원 연결 상태에서만 기능을 켠다).
- **C7 지연**: 웹과 같은 지점 맞춤(#96, 중앙값 차이 ±0.2초)을 유지한다.
- **C8 안정성**: 1시간 연속에서 누적 지연 증가 없음, 메모리 증가 ≤ 50MB, 열 상태로 인한 성능 저하 시 브레이커가 스스로 끈다.

C4의 1dB, C2의 분당 60회는 이번에 처음 정한 값이다. 3·5단계에서 실제 화면을 보고 다시 맞춘다. 합성 장면 PSNR은 체감 화질을 대신하지 못한다. 비교·회귀 확인용 지표로만 쓴다.

## 3. 단계별 계획

### 0단계 — 측정 도구·보고서 (완료, #99)

VT 저지연 보간·프레임률 변환·WebGPU 블록 매칭을 쟀고, 앱 통합을 보류했다.

### 1단계 — 보호 장치·서킷브레이커·GPU 모델 시간 (이번 작업)

- 목표: 보간기와 무관한 보호 장치의 효과, 마감 서킷브레이커의 동작, 1080p 신경망 보간의 GPU 하한 시간, Metal 4 경로의 가능성을 이 Mac에서 확인한다.
- 산출물: `bench.m --guards / --cuts / --rt --breaker`, `rife-mpsgraph.m`, `mps-ops-micro.m`, `mpp-conv-micro.m`, `run-plan.sh`, 이 문서, 원시 로그.
- 성공 기준: 보호 장치가 C3를 지키면서 C4·C5에 다가가는지 수치로 보인다. 브레이커가 희망 없는 경우를 막고 정상 경우를 지킨다. RIFE GPU 1080p 시간을 C1과 비교한다.
- 결과: 4장. 장면 전환·정지 보호·브레이커는 2단계 이후에도 그대로 쓴다. conf와 Metal 4 MPP는 결론을 내지 못했다.

### 2단계 — 신세대 기기 재측정

- 목표: 결론을 바꿀 가장 큰 변수인 칩 세대 차이를 잰다. 이 Mac의 수치를 TOPS로 환산하지 않는다.
- 대상: M3 계열 1대 이상, M4 Pro/Max 1대 이상, 가능하면 M5(GPU Neural Accelerators). 기기는 사용자가 정한다.
- 산출물: 기기별로 `run.sh`(VT 크기별·비동기·FRC)와 `run-plan.sh`(보호 장치·실시간·RIFE GPU) 로그, 요약 표.
- 성공 기준: VT 1080p p95 ≤ 12ms(60→120) 또는 ≤ 25ms(30→60). 또는 RIFE 빠른 구성 1080p가 같은 기준을 넘는다. 같은 기기에서 C2.
- 리스크: VT 내부 모델·예산이 OS 판마다 바뀐다(macOS 버전도 기록). 다른 앱 부하가 수치를 흔든다(유휴·실사용 두 조건으로 잰다).
- 중단 기준: M4 Pro와 M5에서 두 경로 모두 1080p p95 > 25ms면 1080p 실시간 보간을 접는다. 시나리오 A(720p 이하·VOD·정지 화면이 적은 콘텐츠)만 남긴다.

### 3단계 — 학습 가중치로 화질·정합 검증 (첫 실측 완료, 4.6절)

- 목표: RIFE 4.25 / 4.25.lite를 실제 가중치로 돌려 화질과 수치 정합을 확인한다. GPU 경로 채택 여부를 화질로 판단한다.
- 라이선스: Practical-RIFE 저장소·가중치 모두 MIT(README에 가중치 링크도 같은 MIT라고 적혀 있음). UPR-Net은 CC BY-NC-ND 4.0이라 변환·동봉이 불가해 후보에서 뺀다. rife-mlx·`mlx-community/RIFE-4.25`도 MIT.
- 방법: 가중치(약 23MB)와 `IFNet_HDv3.py`는 저장소 밖(`/Volumes/ssd2` 또는 세션 스크래치)에 두고 커밋하지 않는다. 기준 출력은 PyTorch CPU FP32(가상환경 설치 필요). `rife-mpsgraph.m`에 가중치 읽기와 재배열(위상 분해 전치 합성곱·출력 분리)을 넣는다.
- 성공 기준: MPSGraph FP32 대 PyTorch 최대 오차 ≤ 1e-3, FP16 ≤ 1e-2이고 NaN 없음. 합성 장면에서 C3, 보호 장치 포함 C4·C5. 전체 PSNR이 VT 대비 −0.5dB 이상. 공개 영상(bipbop 등)에서 VT보다 나쁘지 않을 것.
- 리스크: 합성 장면이 학습 분포와 달라 실제보다 나쁘거나 좋게 나올 수 있다(실제 방송 표본을 추가한다). FP16 흐름 발산(연구 보고서 4.3절)은 FP32 워핑으로 막는다(이 Mac은 비용 차이가 없음).
- 중단 기준: 보호 장치를 넣어도 C4가 VT보다 나쁘다. 또는 FP32에서도 정합이 1e-2를 넘는다(구조 해석 오류).
- 진행(2026-11-22): 사용자 승인으로 가중치를 받았다. PyTorch는 설치하지 않고, 받은 모델 코드를 읽어 PyTorch 연산 의미대로 CPU 기준 구현을 만들어 대조했다. FP32 정합 ✓, FP16 ✗. 화질은 VT보다 좋고 중단 기준에 걸리지 않는다. C4는 1080p 30→60(전환 없음)에서만 통과했고, 타이머·60→120 채팅이 남았다.

### 4단계 — Metal 단일 타임라인 프로토타입

- 목표: 디코더 출력 NV12(IOSurface) → GPU 색 변환 → 모델 → 워핑·보호 장치(MSL) → NV12/표시까지를 한 커맨드 큐에서 돌려, 종단 시간과 CPU를 잰다.
- 경로 후보: (가) MPSGraph(이번 빠른 구성), (나) Metal 4 MPP `convolution2d`/`matmul2d`를 MSL 안에서 직접 사용(이번에 실행은 확인, 정합 미해결), (다) Core ML → `metal-package-builder` → `MTL4MachineLearningCommandEncoder`(도구 설치 필요).
- 산출물: 독립 명령줄 도구. 보호 장치를 MSL로 옮긴다(현재 CPU 10코어 병렬 1080p: cut + static 약 3.0ms, conf 포함 약 5ms).
- 성공 기준: 대상 기기에서 C1(보호 장치 포함), 보호 장치 GPU 비용 ≤ 1ms, CPU ≤ 1코어의 15%, GPU 증가 ≤ 20%p(C6).
- 리스크: MPP 텐서 연산의 인덱스 규약이 문서화돼 있지 않다. Neural Accelerators가 없는 M1~M4에서는 MPP가 MPSGraph보다 빠르다는 근거가 없다(이번 측정에서 동급). WebKit 합성·다른 GPU 작업과 경합한다.
- 중단 기준: 대상 기기에서 종단 p95가 B를 넘는다.

### 5단계 — 네이티브 재생 실험 앱 (앱 코드 밖)

- 목표: 보간할 프레임을 앱이 직접 쥐는 재생 경로를 검증한다. 현재 WKWebView + hls.js(MSE)는 디코드 프레임이 WebKit GPU 프로세스 안에 있어 꺼낼 수 없다.
- 방법: AVPlayer + `AVPlayerItemVideoOutput`(로컬 MP4에서 +33~200ms 앞선 프레임을 0.04ms에 꺼낼 수 있음을 사용자의 별도 검증에서 확인) 또는 `VTDecompressionSession`. 표시는 `AVSampleBufferDisplayLayer`/`CAMetalLayer`, 120Hz 페이싱은 `CADisplayLink`. 표시·보간 스레드는 실시간 정책(1단계 발견 5). 공개 LL-HLS 테스트 스트림을 쓴다. 치지직은 로그인 없이 공개 방송 시청만 한다.
- 성공 기준: 1시간 연속에서 C2·C7·C8. 오디오·영상 차이 ±20ms 이내. seek·화질 전환·불연속·재연결 때 오래된 보간 결과가 새 화면에 섞이지 않는다(세대 번호).
- 리스크: hls.js 포크에 맞춘 저지연 제어(#96~#97)를 새로 만들어야 한다. ABR 정책이 달라진다. 치지직 LL-HLS를 AVPlayer가 받아들이는지 아직 모른다.
- 중단 기준: A/V 동기 또는 지연 목표를 지킬 수 없다.
- 진행(2026-11-22, 중간): 실험 도구 [`tools/vfi-native-player`](../../tools/vfi-native-player/README.md)를 만들었다. 치지직 LL-HLS를 AVPlayer로 직접 재생할 수 있고(지연 3.4~3.6초 일정), 출력 순서·세대 처리가 지켜짐을 확인했다. 720p60 라이브에서 마감 서킷브레이커 조정이 남았다. [중간 기록](vfi-native-player.md).

### 6단계 — 앱 기능 플래그 (조건부)

- 목표: '부드러운 화면(실험)'을 기본 꺼짐으로 넣는다. 단일 주 패인, 전원 연결, 지원 칩·해상도는 실행 중 측정(시작 5초 + 브레이커)으로 판별한다. 멀티라이브·창 가림·배터리 사용 중에는 끈다. macOS 26 미만에서 링크·실행이 깨지지 않아야 한다.
- 성공 기준: 기존 성능 회귀 검사 통과, 켜고 끌 때 재생 끊김 없음, 5단계 기준 유지.
- 중단 기준: 회귀가 생긴다. 또는 사용자 체감 시험에서 글자 깜박임이 보고된다.

### W단계 — Windows

- 목표: 같은 모델(ONNX로 내보낸 RIFE)과 같은 보호 장치를 DirectML(공통)·TensorRT(NVIDIA)로 돌린다. NVIDIA Optical Flow SDK FRUC(RTX)도 조사한다. WebView2 재생도 네이티브 디코드 경로가 필요하다는 점은 macOS와 같다.
- 시작 조건: 3단계 성공. 산출물: Windows 빌드 서버에서 도는 측정 도구, 같은 합성 장면 지표.
- 성공 기준: 같은 장면에서 macOS 대비 PSNR ±1dB, 대상 GPU에서 C1.
- 중단 기준: 대표 GPU(내장 그래픽 포함)에서 C1 미달이면 NVIDIA RTX 전용으로 범위를 줄이거나 접는다.

## 4. 실측 결과 (1단계 4.1~4.5, 3단계 4.6)

### 4.1 보호 장치 화질 (VT 저지연 보간, 합성 장면)

합성 장면은 #99와 같다(팬 배경 1200px/s, 회전 막대, 빠른 공 2400px/s, 반투명 채팅 상자, 고정 자막, 프레임마다 바뀌는 타이머). `--cuts N`은 입력 N장마다 배경·막대·공만 다른 장면으로 바꾸고, 방송 화면에 박힌 타이머·채팅·자막은 그대로 둔다. 실제 방송처럼 HUD는 유지되고 게임 화면만 끊기는 상황이다. 정답 대비 휘도 PSNR(dB), 장 단위 평균이다.

권장 조합은 **VT + cut + static**이다(장면 전환이 없으면 static과 같다). 판정은 C3·C4 기준이다.

값은 dB다. 글자 영역 칸은 `VT → 권장 (그대로 두기)` 순서다.

| 조건 | 전체: 그대로 / 섞기 / VT / 권장 | 빠른 공: 그대로 / VT / 권장 | 채팅 | 자막 | 타이머 | C3 / C4 |
| --- | --- | --- | --- | --- | --- | --- |
| 720p 30→60, 전환 없음 | 21.4 / 24.0 / 26.1 / **26.7** | 22.2 / 34.7 / 34.7 | 18.9 → 19.1 (17.1) | 23.9 → 26.4 (30.8) | 15.0 → 17.2 (19.8) | ✓ / ✗ 자막 −4.3, 타이머 −2.6 |
| 720p 30→60, 15장마다 전환 | 20.9 / 23.3 / 24.4 / **25.4** | 21.2 / 32.7 / 32.8 | 17.9 → 18.0 (17.4) | 20.0 → 23.3 (30.0) | 14.7 → 17.0 (19.9) | ✓ / ✗ 자막 −6.6, 타이머 −2.8 |
| 720p 60→120, 30장마다 전환 | 23.4 / 25.8 / 27.6 / **28.0** | 23.6 / 37.2 / 37.3 | 20.0 → 20.2 (20.5) | 26.5 → 28.4 (32.1) | 18.6 → 19.3 (21.1) | ✓ / ✗ 자막 −3.7, 타이머 −1.8 |
| **1080p 30→60, 전환 없음** | 21.1 / 23.9 / 29.8 / **30.1** | 22.1 / 36.3 / 36.3 | 23.2 → 23.5 (16.6) | 28.4 → 30.6 (30.7) | 18.9 → 19.2 (19.7) | **✓ / ✓** |
| 1080p 30→60, 15장마다 전환 | 20.6 / 23.2 / 27.9 / **28.7** | 21.0 / 32.8 / 33.0 | 23.1 → 23.1 (16.9) | 27.8 → 30.3 (30.0) | 15.8 → 17.4 (19.8) | ✓ / ✗ 타이머 −2.4 |
| 1080p 60→120, 30장마다 전환 | 24.3 / 25.4 / 28.3 / **28.8** | 23.3 / 39.6 / 39.7 | 20.8 → 21.2 (31.3) | 28.8 → 31.2 (31.9) | 18.9 → 19.5 (21.0) | ✓ / ✗ 채팅 −10.1, 타이머 −1.4 |

- VT만 쓰면 6개 조건 모두 C4에서 떨어진다(가장 나은 1080p 30→60도 자막 −2.4dB). 권장 조합은 1080p 30→60 전환 없음에서 C4를 통과하고, 나머지는 타이머·자막·60→120 채팅에서 떨어진다. 움직임 이득(C3)은 모든 조건에서 남는다(빠른 공 +11.7~+16.4dB, 전체 +2.0~+6.2dB).
- 정지 보호가 더한 값(권장 − VT): 자막 +1.9~+3.3dB, 타이머 +0.3~+2.4dB, 빠른 공 −0.05~+0.2dB.
- 720p 행은 720p로 그린 장면을 720p로 보간한 결과다. 1080p를 720p로 줄여 보간하는 우회(#99)와는 다르다. 화소가 적을수록 글자 획이 가늘어 보간이 더 쉽게 무너진다.

- 장면 전환 감지: 6개 조건 16쌍을 모두 감지했고 오검출은 0이다. 정상 쌍의 축소 SAD 최대 0.089로 문턱 0.10에 가깝다. 히스토그램 거리는 정상 최대 0.118, 전환 최소 0.827로 크게 갈린다. **SAD 하나만 쓰면 빠른 팬에서 오검출할 수 있어 두 조건을 함께 쓴다.** 전환 쌍 전체 PSNR은 보간 18.6~19.3dB에서 그대로 두기와 같은 20.7~24.7dB로 돌아온다. 합성 장면은 전환이 선명하므로 실제 방송(페이드·플래시·부분 전환)에서 문턱을 다시 잡아야 한다.
- 정지 보호: 3×3 침식을 하면 가는 글자 획까지 보호에서 빠져 효과가 사라졌다(720p 자막 +0.0dB). 그래서 침식을 끈다. 정지 판정 길이를 4장으로 고정하면 1080p 60→120에서 빠른 공 영역이 3.1dB 깎였다. 시간 기준(120ms, 60fps에서 7장)으로 바꾸자 손실이 0.1dB 미만으로 줄었다.
- conf(설명 안 되는 변화): 이동 하나로 판단하면 1080p 30→60 채팅이 23.2 → 16.9dB로 크게 망가진다. 반투명 상자 안에서 느린 글자와 빠른 배경, 두 층이 겹치기 때문이다. 두 층 모델(정지·최선 이동·두 번째 이동 중 화소별 최소)로 바꿔도 −2.8dB가 남는다. 반대로 60→120 채팅은 +4.3dB로 살린다. 장면에 따라 득실이 엇갈려 권장 조합에서 뺐다.
- 남은 실패: **타이머**(프레임마다 바뀌는 숫자)는 정지 보호로 막을 수 없다. 1080p 30→60 전환 장면에서 그대로 두기보다 2.5dB 낮다. **60→120 채팅**은 VT 자체가 그대로 두기보다 10dB 낮아 정지 보호로도 회복되지 않는다. 둘 다 '이 영역은 보간하지 않는다'를 신뢰도 있게 판단해야 하는 문제다. 3단계 모델의 흐름·마스크·워핑 잔차로 다시 시험한다.
- 비용: CPU 10코어 병렬 구현으로 입력 1장당 1080p 휘도·축소·히스토그램 2.2ms, 정지 마스크 0.7~0.8ms, conf 탐색 1.7~2.1ms다(720p는 1.0 / 0.4 / 1.1~1.2ms). 권장 조합(cut + static)은 1080p 약 3.0ms다. 실제 경로에서는 디코더 NV12의 Y 평면을 바로 쓰고 GPU로 옮긴다(4단계).

### 4.2 실시간 모사와 서킷브레이커 (VT 저지연 보간)

절대 시간표로 입력이 도착하고, 동시에 1건만 비동기로 처리한다. 바쁘면 그 쌍은 건너뛴다. 마감(도착 + B)을 넘긴 보간은 버린 것으로 센다. 측정 스레드는 시간 제약 정책(도착 흔들림 p95 0.02~0.04ms)으로 돌렸다.

제때 보간은 전체 쌍 대비, 버린 보간은 요청한 것 대비 비율이다. 전환/분은 '보간이 보인 쌍 ↔ 원본만 보인 쌍'이 바뀐 횟수다. CPU는 측정 프로세스 전체(1코어 = 100%)다.

| 조건 | 브레이커 | 제때 보간 | 버린 보간 | 바빠서 건너뜀 / 차단 / 열림 | 전환/분 | 처리 ms p50 / p95 / p99 / 최대 | CPU | C2 |
| --- | --- | ---: | ---: | --- | ---: | --- | ---: | --- |
| 720p 60→120 | 끔 | 99.0% | 0.5% | 9 / 0 / 0 | 36 | 9.6 / 11.8 / 15.4 / 24.4 | 4% | ✓ |
| 720p 60→120 | v1 | 95.6% | 0.6% | 11 / 58 / 1 | 36 | 9.5 / 11.4 / 15.6 / 25.1 | 4% | ✓(경계) |
| 720p 60→120 | **v2** | **99.9%** | 0.1% | 1 / 0 / 0 | 4 | 9.5 / 11.3 / 13.5 / 17.1 | 4% | ✓ |
| 1080p 30→60 | 끔 | 0% | 100% | 407 / 0 / 0 | 0 | 93.8 / 111.5 / 119.0 / 142.9 | **68%** | ✗ |
| 1080p 30→60 | v2 | 0% | 100%(13건) | 42 / 545 / 5 | 0 | 116.9 / 166.5 / 189.8 / 189.8 | **5%** | ✗(처리 시간), 헛된 부하 차단 ✓ |
| 720p 60→120 + ANE 경합 | 끔 | 100% | 0% | 0 / 0 / 0 | 0 | 8.1 / 13.0 / 14.6 / 16.0 | 2% | ✓ |
| 720p 60→120 + ANE 경합 | v2 | 99.9% | 0.1% | 1 / 0 / 0 | 2 | 8.1 / 13.2 / 14.6 / 19.0 | 2% | ✓ |

같은 설정의 앞선 반복([`raw/realtime-v1-rtthread.txt`](vfi-dev-plan-2026-11-22/raw/realtime-v1-rtthread.txt))에서는 v1이 3번 열려 제때 보간이 99.1%(끔) → 76.1%였다. 1080p 30→60에서 v1은 요청 5건, CPU 2%였다.

720p 60→120은 처리 시간만 보면 이 Mac에서 C2를 통과한다. 하지만 4.1절의 화질 기준(C4)에서 떨어진다.

- 1080p 30→60은 브레이커가 없으면 처리할 때마다 늦어(제때 0%) CPU 1코어의 68%와 ANE를 헛쓴다. 브레이커는 첫 결과(> 2·B)에서 바로 열고 1·2·4·8초 간격으로만 다시 시도해 CPU를 2%로 줄인다. 다시 시도한 첫 요청은 0.16~1.1초 걸렸다(ANE가 쉬다 깨어남).
- 720p 60→120 정상 상황에서 v1 규칙(8건 창, 마감 초과 2건이면 열림)은 1~3번 열려 제때 보간을 95.6~76.1%로 깎았다. v2(0.5초 창, 초과 10%, 재시도 직후 2건 유예)는 한 번도 열리지 않았다(99.9%, 전환 분당 4회).
- ANE 경합: 다른 프로세스가 1080p 보간으로 ANE를 계속 쓰는 동안에도 720p 60→120은 100% 제때였다. 처리 시간도 줄었다(p50 8.1ms). 앱 하나의 보간 부하로는 ANE 용량이 부족하지 않고, 쉬는 사이 전원 상태 변화가 지연을 만든다. 같은 앱의 멀티라이브(패인 여러 개)가 ANE를 나눠 쓸 때의 화질·지연은 따로 재야 한다.
- 첫 시도(v1 로그, 일반 스레드)는 측정 스레드가 평균 4.5ms 늦게 깨어나 720p 60→120 제때 보간이 57%로 나왔다. 측정 방법의 오류였으므로 판단에 쓰지 않는다([`raw/realtime-v1.txt`](vfi-dev-plan-2026-11-22/raw/realtime-v1.txt)).

### 4.3 RIFE 4.25 구조의 GPU 시간 (MPSGraph, 무작위 가중치)

TNTwise/rife-ncnn-vulkan(MIT)에 있는 `rife-v4.25` / `rife-v4.25-lite`의 `flownet.param` 층 구성을 그대로 옮겼다. 매개변수 수 5.66M은 공개 값과 같다. 처리 시간은 가중치 값과 무관하므로 학습된 가중치는 받지 않았다. 출력 화질은 의미가 없다. 시간은 인코딩 + GPU + 완료 대기의 벽시계 시간이며, 입력 색 변환(약 0.3ms)은 빠져 있다.

| 구성 (FP16, 50회) | 720p p50 / p95 | 1080p p50 / p95 | 합성곱 GMAC |
| --- | ---: | ---: | ---: |
| 원래 구성 그대로 | 37.4 / 41.4 | 79.0 / 88.0 | 46.4 |
| 빠른 구성 phase(계산량 같음) | 22.2 / 25.2 | 43.5 / 44.6 | 46.4 |
| 빠른 구성 3x3(전치 합성곱을 3×3 하나로, 계산량 1.2배) | 19.4 / 20.4 | 40.0 / 43.8 | 55.5 |
| 3x3 + 4.25.lite | — | 34.1 / 36.0 | 29.4 |
| 3x3 + scale 0.5(흐름을 절반 해상도에서) | — | **24.4 / 25.7** | 20.8 |
| 3x3 + lite + scale 0.5(패딩 2048×1280) | — | 26.6 / 31.0 | 15.9 |
| 3x3, 워핑만 FP32 | — | 43.3 / 45.2 | 55.5 |
| 3x3, 전부 FP32 | — | 43.0 / 45.6 | 55.5 |

- 빠른 구성은 학습된 가중치를 재배열하면 원래 IFNet과 같은 값을 낸다. 전치 합성곱(k4 s2 p1)은 출력 위상 4개의 2×2 합성곱 + depthToSpace와 같다. 블록 출력 13채널은 처음부터 흐름 2+2·마스크 1·특징 8로 나눠 만들어 전체 해상도 slice를 없앤다. 영상과 Head 특징을 한 번만 이어 붙여(7채널) 블록당 워핑 4회를 2회로 줄인다. 축소하는 블록은 입력을 먼저 줄인 뒤 작은 해상도에서 이어 붙인다. 정합은 3단계에서 실제 가중치로 확인한다.
- scale 0.5는 Practical-RIFE가 4K에 권하는 설정이다. 1080p에서는 흐름 해상도가 낮아져 작은 물체·가는 글자 화질이 떨어질 수 있다(3단계에서 확인).
- 판정: M1 Max GPU에서는 어떤 구성도 60→120 목표(p95 ≤ 12ms)에 닿지 않는다. 30→60 목표(≤ 25ms)도 scale 0.5가 p95 25.7ms로 아깝게 넘는다. 보호 장치·색 변환·WebKit 합성 경합을 더하면 더 멀어진다.

### 4.5 Metal 4 경로 확인

- `MTLGPUFamilyMetal4`: M1 Max에서 지원(1). 헤더: `MTLTensor.h`, `MTL4MachineLearningCommandEncoder.h`, `MetalPerformancePrimitives`(`convolution2d`, `matmul2d`)가 SDK에 있다.
- MSL 안의 MPP `convolution2d`: Xcode의 오프라인 Metal Toolchain이 설치돼 있지 않다(`xcodebuild -downloadComponent MetalToolchain` 필요). 대신 OS 런타임 컴파일러(`newLibraryWithSource`, MSL 4.0)로 빌드해 실행했다. 1080p RIFE 층 모양 4개에서 0.60~0.94ms(2.6~4.3 TFLOPS), MPSGraph 같은 층 0.56~0.84ms로 같은 수준이다.
- **정합 실패**: 같은 입력·가중치에서 MPSGraph는 CPU 정답과 최대 차이 0.0002였지만 MPP 출력은 1.6이었다. 가중치 배치 7가지 × 출력 위치 이동 9가지, slice 방식과 `set_offsets` 방식을 모두 대조해도 맞는 규약이 없었다. 헤더에 패딩·타일 원점 설명이 없고 구현은 드라이버 안 외부 함수다. 규약을 확정하기 전에는 MPP의 속도 수치도 참고로만 본다.
- `MTL4MachineLearningCommandEncoder`: 파이프라인이 Core ML 모델을 Metal 패키지로 바꾼 함수(`MTL4FunctionDescriptor`)를 요구한다. 이 Mac에는 변환 도구(`metal-package-builder`)도 `coremltools`도 없다. M1에는 GPU Neural Accelerators가 없어, 이 경로의 이득(연구 보고서 5.3절)은 M5에서만 기대할 수 있다.

### 4.6 3단계 첫 실측 — RIFE 4.25 / 4.25.lite 학습 가중치

**가중치와 변환**

- 출처: Practical-RIFE README의 공식 Google Drive 링크. 4.25(2024-09-19)와 4.25.lite(2024-10-20)다. README는 링크 내용이 프로젝트와 같은 MIT라고 밝힌다.
- 받은 파일(SHA-256): 4.25 zip 22,919,050 B `e63d481b7ae5d4a4e6ad7ac5b410ff78f3bf7be3b51b2e38ca8152747abde5b4`, 4.25.lite zip 22,765,148 B `e84366c23e0eb1a637a55aad2e4f3442ec2bf4c388043b4aabbf590be289e6e8`. 저장 위치는 저장소 밖 `/Volumes/ssd2/cview-vfi/weights/`다. zip 안의 `IFNet_HDv3.py`·`RIFE_HDv3.py`는 실행하지 않고 읽기만 했다. 구조와 scale_list가 1단계 복제본과 같았다.
- 변환: [`rife-export.py`](../../tools/frame-interp-lab/rife-export.py)가 torch 없이 `flownet.pkl`(PyTorch zip 형식)을 원시 float32와 이름표로 바꾼다. 허용 목록 언피클러를 써서 텐서 재구성 외의 코드는 실행하지 않는다. 텐서 198개 중 `teacher`·`caltime`(학습 때만 쓰는 증류용)은 추론에 쓰지 않는다.

## 5. 보호 장치 현재 값

| 장치 | 동작 | 값 |
