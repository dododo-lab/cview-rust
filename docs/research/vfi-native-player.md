## 1. 결론

1. **보간할 프레임을 앱이 직접 쥐는 재생 경로가 동작한다.**
   - AVPlayer + `AVPlayerItemVideoOutput`으로 디코드 프레임을 앞당겨 받는다.
   - 받은 프레임을 VT 저지연 보간(ANE)·장면 전환 감지·정지 화소 보호를 거쳐 원본·중간 프레임으로 PTS 순서대로 내보낸다.
   - 최종 측정 18회(메모리 진단 2회 별도) 모두 순서 위반 0, 이전 결과 혼입 0, 받은 프레임 대비 원본 손실 0이었다. 탐색·화질 전환·프레임률 변화·불연속·지연 주입을 모두 포함한 결과다.
2. **치지직 LL-HLS를 AVPlayer가 받아들인다(계획의 가장 큰 미확인 위험 해소).**
   - 로컬 프록시 없이 CDN에서 직접 재생했다. 로그인 없이 공개 방송만 봤다.
   - 1시간 동안 멈춤·재연결이 없었고, 지연(PDT 기준)이 3.65→3.73초로 늘지 않았다.
   - 메모리는 1시간에 59.7MB 늘었다. 이는 AVPlayer 단독 재생에서도 생기는 LL-HLS 요청 기록 때문이다(4.1절).
   - 다만 AVPlayer 기본 설정 그대로는 30초쯤 뒤 멈춘 채 회복하지 못했다. 필요한 설정 3가지는 5장에 있다.
3. **이 Mac에서 720p60→120 라이브 보간은 '대부분 된다'이다. C2를 안정적으로 넘지는 못한다.**
   - 치지직 10분: 제때 92.1%, 늦음 0.2%, 전환 분당 6.8회
   - 치지직 1시간: 제때 83.2%, 늦음 0.4%, 전환 분당 13.7회
   - Mux LL-HLS 2분: 95.5%
   - 파일 1분: 99.9~100%
   - 놓친 부분은 대부분 ANE가 다른 앱과 경합해 일시적으로 멈춘 구간이다. 마감 서킷브레이커가 그 구간에서 보간을 쉬었다.
4. **1080p60은 이 Mac에서 안 된다.** VT 1건이 p50 107ms였다. 브레이커가 보간을 계속 꺼 둬 ANE를 아꼈다. 1·3단계 결론과 같다.
5. **앱 통합(6단계)은 계속 보류한다.**
   - 남은 조건 1: 2단계(신세대 기기 재측정)
   - 남은 조건 2: 5단계의 A/V 동기(±20ms)·실제 표시 시각·웹 대비 지연(C7). 창을 띄우는 측정이라 이번에 하지 않았다.
   - 이 Mac만 보면 720p 이하·전원 연결·단일 패인 조건의 실험 기능은 기술적으로 가능하다.

## 2. 도구 구조

자세한 설계는 [README](../../tools/vfi-native-player/README.md)에 있다. 핵심은 다음과 같다.

- **앞당겨 받기.** `copyPixelBufferForItemTime:`은 질의 시각 이하의 가장 늦은 프레임을 주고, 그 앞 프레임은 말없이 버린다. 그래서 `hasNewPixelBufferForItemTime:`을 이분 탐색해 다음 프레임만 받는다.
  - 표시보다 최대 150ms 앞서 받는다.
  - 받기 스레드는 실시간 정책(`THREAD_TIME_CONSTRAINT_POLICY`)으로 돈다.
- **마감.**
  - 중간 프레임 마감은 '호스트 시각(중간 PTS) − 5ms'이다. 아이템 시계의 현재 속도로 계산한다.
  - 마감을 넘긴 짝은 원본만 내보낸다. VT 요청은 한 번에 1건이다.
  - 최근 3초 처리 시간 p75 안에 끝낼 수 없는 짝은 넣지 않는다.
- **세대 번호.**
  - hard 변경(탐색·출력 비움·시간 점프·역행 PTS·재연결): 미처리 프레임을 버리고 출력을 비운다.
  - soft 변경(크기·프레임률): 남은 프레임을 원본으로 내보낸다.
  - 처리 중이던 이전 세대 결과는 버린다.
  - 한 번의 탐색이 보내는 두 알림(time_jumped, output_flushed)은 합친다.
- **집계.** 짝을 한 곳에서 같은 순서로 분류한다. '보간 대상 짝 = 결과 항목의 합'(accounting_ok)이 모든 실행에서 맞았다.
- **마감 서킷브레이커 v3.** 연구 계획 1단계의 v2를 이 구조에 맞게 고쳤다(5장 7번).

### 4.1 메모리 증가의 원인 — AVPlayer의 LL-HLS 요청 기록

1시간 동안 메모리가 59.7MB(측정 기록 제외) 늘어 C8(≤ 50MB)을 넘었다. 원인을 가리려고 `heap` 명령으로 2분과 10분 시점을 찍어 클래스별로 비교했다([`raw/memdiag/heap-diff.md`](vfi-native-player-2026-11-22/raw/memdiag/heap-diff.md)).

| 치지직 720p60, 약 9분 | 메모리 증가(측정 기록 제외) | 늘어난 HTTP 거래 객체 |
| --- | ---: | --- |
| m1 보간 전체 | 6.6MB | `CFHTTPMessage` 2,930, `__CFN_TransactionMetrics`·`nw_data_transfer_report`·`FigMetricEvent` 각 977 |
| m2 기준(보간·보호 끔, AVPlayer 단독) | 10.6MB | `CFHTTPMessage` 2,941, 나머지 각 979~980 |

- 늘어난 것의 대부분은 AVPlayer가 LL-HLS의 파트·재생 목록 요청(초당 약 2건)마다 남기는 거래 기록이다(CFNetwork·Network·CoreMedia).
- 보간을 끈 AVPlayer 단독 재생도 같은 비율로 늘었다. **보간 파이프라인이 더한 증가는 없다.**
- 보간 쪽에서 늘어난 객체는 ANE 런타임(Espresso)뿐이다. 이는 VT 세션 수(m1은 화질 변경으로 4개)에 비례하고, 그 뒤로는 늘지 않는다.
- 앱의 네이티브 재생 경로에서도 AVPlayer를 쓰면 같은 증가가 생긴다. 줄이려면 AVPlayer 지표 수집을 끄는 방법을 찾거나(확인 못 함), 오래 재생할 때 아이템을 주기적으로 다시 만드는 방안을 시험해야 한다.

## 5. 실측하며 알게 된 사실(개발 중 고친 것 포함)

1. **단독 `AVSampleBufferVideoRenderer`는 표시 대상이 없으면 `enqueueSampleBuffer:`에서 예외를 던진다.** 창 없이 재려면 창에 붙이지 않은 `AVSampleBufferDisplayLayer`의 `sampleBufferRenderer`를 쓴다. 동기화기는 아이템 시계에 맞춰 둔다.
2. **치지직 LL-HLS를 AVPlayer로 안정 재생하려면 세 가지가 필요했다.**
   - `configuredTimeOffsetFromLive`를 PART-HOLD-BACK(3.05초)보다 길게 둔다(3.5초). 3초면 오류 -12640 "Cannot get that close to live"가 난다.
   - `canUseNetworkResourcesForLiveStreamingWhilePaused = YES`. 기본값 NO면 라이브가 멈춘(속도 0) 동안 받기도 멈춰 버퍼가 다시 차지 않는다. 이때 끊김 알림(`AVPlayerItemPlaybackStalledNotification`)도 오지 않았다. 그래서 멈춤은 `timeControlStatus`로 판단한다.
   - 웹 지연 규칙(앞 버퍼 4초 넘으면 1.03배)을 쓰지 않는다. AVPlayer에서는 앞 버퍼가 늘 4초 근처라 계속 따라잡다가, 버퍼가 갑자기 0이 되며 멈췄다. 지연은 AVPlayer 정책(`automaticallyPreservesTimeOffsetFromLive`)에 맡겼다.
3. **치지직 720p 디코더 버퍼에는 아래쪽 추가 픽셀 16줄이 있다**(`CVPixelBufferGetExtendedPixels` → 0,0,0,16). VT가 요구하는 입력은 추가 픽셀 0이다.
   - 그대로 넣으면 VT 1건이 p50 14.5ms였다. VT 속성의 버퍼로 복사(`VTPixelTransferSession`)하면 9.2ms였다.
   - 360p에서는 그대로 넣으면 오류 -19740이 났다.
4. **그 복사는 프레임이 도착할 때 한 번만 한다.**
   - 짝마다 앞뒤 두 프레임을 복사하면 복사가 VT 처리와 직렬로 이어진다. 그러면 짝 하나에 입력 간격보다 오래 걸려 대기열이 밀렸다(제출 여유 p50 58ms, 치지직 제때 3.8%).
   - 도착 때 한 번(p50 2.2ms, VT와 겹침) 복사하고 다음 짝의 앞 프레임으로 다시 쓰자, 여유가 119ms로 돌아오고 제때가 92.1%가 됐다.
5. **ANE는 드문드문 쓰면 느리다.** 연속 처리 중 720p는 9ms였지만, 사용률 20% 이하의 시험 요청은 15~18ms였다. 쉬었다가 다시 쓴 첫 요청은 수백 ms까지 걸렸다(1단계 측정과 같은 현상).
6. **다른 앱과 ANE를 나눠 쓰면 VT가 간헐적으로 80~340ms 멈춘다.** bipbop·Mux·치지직 모두에서 나타났다. 실행마다 제때 비율을 흔드는 가장 큰 요인이다.
7. **마감 서킷브레이커는 연구 계획 1단계의 v2를 그대로 쓸 수 없었다.** v2는 '도착 + B 마감, 한 건 > 2·B, 평균 > 0.85·B' 규칙이다. 앞당겨 받기 구조에는 마감까지 100ms 안팎의 여유가 있어, v2로는 늦지 않은 결과에도 열렸다. 거쳐 간 결정은 다음과 같다(`work-log.txt`).
   - 늦음은 요청 자체가 느렸던 것(처리 > 0.75·T)만 센다. 앞 요청이 느려 대기열에서 늦게 출발한 짝까지 세면, '열림 → 쉼 → 느린 첫 요청 → 늦음 → 다시 열림'이 반복됐다(치지직 5분에 21~34번).
   - 반쯤 열림: 열린 동안 시험 요청(결과는 버림, ANE 사용률 20% 이하)으로 ANE를 깨워 둔다.
     - 시험 요청은 낮은 클럭 상태라 연속 처리 속도를 보여 주지 못한다. 그래서 '아예 못 따라감'(시험 중앙값 > 2·T, 1080p)만 열린 기간을 늘리고, 나머지는 기간이 끝나면 닫고 다시 시도한다.
     - 닫은 직후 10건은 판단에서 뺀다.
   - 열린 기간은 1·2·4·8·16·30초로 늘린다. 다시 시도할 때마다 보간이 켜졌다 꺼지므로, 계속 실패하면 오래 쉬게 했다.
   - 제출 판단의 예상 처리 시간은 최근 3초 표본의 p75로 한다. 개수로만 자르면 느린 표본에 값이 굳어, 요청을 아예 보내지 않았다(시작 못함 10,716건).
8. **프레임률 변화 감지는 최근 간격의 최솟값으로 한다.** 프레임이 빠지면 간격이 길어지기만 해서, 중앙값을 쓰면 60fps를 30fps로 잘못 읽었다.
9. **화질 전환을 보려면 앞 버퍼를 줄여야 한다.** VOD에서 AVPlayer가 앞 버퍼를 80초쯤 채워, 화질 상한을 바꿔도 새로 받는 구간부터만 반영된다(`--forward-buffer 6`).

## 6. 연구 계획 기준 판정(5단계)

| 기준 | 판정 | 근거 |
| --- | --- | --- |
| C2 실시간(제때 ≥ 95%, 늦음 ≤ 1%, 전환 ≤ 60/분) | 파일 ✓, Mux LL ✓. 치지직 720p60은 늦음·전환 ✓, 제때 92.1%로 미달 | 4장. 미달분은 다른 앱과의 ANE 경합 구간 |
| C6 자원(추가 CPU ≤ 15%p) | ✗(17.6%p) | 3장. 보호 장치를 GPU로 옮기면 줄일 수 있다 |
| C7 지연(웹과 같은 지점, ±0.2초) | 측정 안 함 | 같은 채널을 CView로 동시에 틀고 비교해야 한다. 이번에는 지연이 3.2~3.7초로 일정함만 확인했다 |

| A/V ±20ms | 측정 안 함 | 창 없는 모드에서는 영상 시계가 정의상 아이템 시계와 같다. 창 모드(`--sink window`)로 사용자가 직접 확인해야 한다 |
| 이전 결과 혼입 없음(세대 번호) | ✓ | 최종 18회 모두 순서 위반 0. 지연 주입·탐색·화질·프레임률·불연속·재연결 포함 |

## 7. 다음 단계

1. **2단계(신세대 기기 재측정)가 여전히 가장 큰 변수다.**
   - `run.sh <폴더>`와 `summarize.py`로 같은 표를 만든다.
   - 다른 앱의 ANE 사용 여부(Vitals `system_status`의 `neural_engine.apps_using_it`)를 함께 기록한다.
2. **창 모드 확인(사용자 실행).**
   - `vfi-player --chzzk popular --sink window`로 실제 화면의 부드러움과 A/V 동기를 눈으로 본다.
   - `i` 키로 보간을 켜고 끄며 비교한다.
   - 객관 지표가 필요하면 `CAMetalLayer` 표시 시각 기록을 더한다.
3. **C6을 맞추려면 보호 장치(cut·static)를 MSL로 옮긴다.** 4단계 계획과 같다.
4. **6단계(앱 기능 플래그)는 2단계 결과를 본 뒤에 다시 판단한다.** 이 Mac만 보면 720p 이하·전원 연결·단일 패인 조건으로 제한된다.

## 8. 재현

```sh
tools/vfi-native-player/run.sh /tmp/vfi-runs                     # long 을 뺀 전부(약 36분)
tools/vfi-native-player/run.sh /tmp/vfi-runs-long long           # 치지직 1시간
python3 -I tools/vfi-native-player/summarize.py /tmp/vfi-runs     # 마크다운 표
```

- VT 세션은 샌드박스 안에서 시작되지 않을 수 있다. 일반 터미널에서 실행한다.
- 치지직은 로그인 없이 공개 방송(성인·유료·암호화 제외)만 본다. 재생 주소의 토큰과 채널 id는 출력·기록하지 않는다.
- 실행마다 다른 앱의 ANE·CPU 부하에 따라 제때 비율이 크게 흔들린다(bipbop 73~98%). 같은 조건을 두 번 이상 재서 비교한다.
