## 1. 지금까지의 결론

1. **보간할 프레임을 앱이 직접 쥐는 재생 경로는 동작합니다.**
   - AVPlayer + `AVPlayerItemVideoOutput`으로 파일·HLS VOD·LL-HLS 라이브·치지직 공개 방송을 재생하면서 VT 저지연 보간을 넣었습니다.
   - 원본·중간 프레임을 PTS 순서로 내보냈고, 모든 실행에서 순서 위반 0이었습니다.
   - 탐색·화질 전환·프레임률 변화·불연속·재연결에서 이전 결과가 새 화면에 섞인 경우도 0이었습니다(세대 번호).
2. **치지직 LL-HLS를 AVPlayer가 받아들입니다(계획의 미확인 위험 해소).**
   - 로컬 프록시 없이 CDN에서 직접 재생했습니다.
   - 4~5분 동안 지연(PDT 기준)이 3.4~3.6초로 처음과 끝이 같았고, 메모리도 늘지 않았습니다.
   - 다만 기본 설정 그대로는 30초쯤 뒤 멈춘 채 회복하지 못했습니다(3장).
3. **이 Mac에서 720p60→120은 경계입니다.** 연속 처리 중 VT 1건은 p50 9ms(입력 간격 16.7ms)입니다. 그러나 ANE가 가끔 수십~수백 ms 멈추고, 쉬면 느려집니다. 그래서 C2(제때 ≥ 95%)는 파일·VOD에서는 넘고, 치지직 라이브에서는 아직 안정적으로 넘지 못했습니다. 4장의 마감 서킷브레이커 조정이 남았습니다.
4. **1080p60은 이 Mac에서 안 됩니다.** VT 1건이 p50 115ms였고, 브레이커가 보간을 껐습니다. 1·3단계 결론과 같습니다.

## 3. 새로 알게 된 사실

1. **단독 `AVSampleBufferVideoRenderer`는 표시 대상이 없으면 `enqueueSampleBuffer:`에서 예외를 던집니다.** 창 없이 재려면 창에 붙이지 않은 `AVSampleBufferDisplayLayer`의 `sampleBufferRenderer`를 씁니다. 동기화기(`AVSampleBufferRenderSynchronizer`)는 아이템 시계에 맞춰 둡니다.
2. **`copyPixelBufferForItemTime:`은 질의 시각 이하의 가장 늦은 프레임을 주고, 그 앞 프레임은 말없이 버립니다.** `hasNewPixelBufferForItemTime:`을 이분 탐색(0.4ms)해 다음 프레임만 받습니다. 받은 프레임과 내보낸 원본 수가 모든 실행에서 같았습니다.
3. **치지직 LL-HLS를 AVPlayer로 안정 재생하려면 세 가지가 필요했습니다.**
   - `configuredTimeOffsetFromLive`를 PART-HOLD-BACK(3.05초)보다 길게(3.5초) 둡니다. 3초로 두면 오류 -12640 "Cannot get that close to live"가 납니다.
   - `canUseNetworkResourcesForLiveStreamingWhilePaused = YES`로 둡니다. 기본값 NO면 라이브가 멈춘(속도 0) 동안 받기도 멈춰 버퍼가 다시 차지 않습니다. 끊김 알림도 오지 않았습니다.
   - 웹 지연 규칙(앞 버퍼 4초 넘으면 1.03배)을 쓰지 않습니다. AVPlayer에서는 앞 버퍼가 늘 4초 근처라 계속 따라잡다가 버퍼가 갑자기 0이 되며 멈췄습니다. 기본값을 AVPlayer 자체 정책(`automaticallyPreservesTimeOffsetFromLive`)으로 바꿨습니다.
4. **치지직 720p 디코더 버퍼에는 아래쪽 추가 픽셀 16줄이 있습니다**(`ext 0,0,0,16`).
   - VT가 요구하는 입력은 추가 픽셀 0입니다.
   - 그대로 넣으면 VT 1건이 p50 14.5ms입니다. VT 속성의 버퍼로 복사(`VTPixelTransferSession`)하면 9.2ms입니다.
   - 360p에서는 그대로 넣으면 오류 -19740이 났습니다.
   - `--vt-input auto`(기본)는 추가 픽셀이 있거나 VT가 거부하면 복사합니다.
5. **ANE는 드문드문 쓰면 느립니다.** 연속 처리 중 720p는 9ms였지만, 사용률 20% 이하의 시험 요청은 약 15ms였습니다. 쉬었다가 다시 쓴 첫 요청은 수백 ms까지 걸렸습니다(1단계 측정과 같은 현상).
6. **실사용 부하에서 ANE는 간헐적으로 80~340ms 멈춥니다**(bipbop·Mux·치지직 모두). 연구 계획의 서킷브레이커 v2(도착 + B 마감, 한 건 > 2·B)는 이 도구의 '앞당겨 받기' 구조와 맞지 않았습니다. 마감까지 여유가 720p60 중앙값 60~100ms인데도, 늦지 않은 결과에 열려 보간을 쉬었습니다.

## 4. 남은 문제 — 마감 서킷브레이커(v3) 조정

치지직 라이브에서 브레이커가 다음 고리를 반복합니다.

1. 열린 동안 ANE가 쉽니다.
2. 닫힌 직후 요청이 느립니다(13~23ms).
3. 대기열이 밀려 늦음이 쌓이고, 다시 열립니다.

시도한 조정은 다음과 같습니다. 모두 소스에 들어 있습니다.

| 실행 | 바꾼 것 | 결과 |
| --- | --- | --- |
| `e1` | 늦음 10% 규칙, 평균 > T 규칙 | 70초까지 100%, 이후 21번 다시 열림 |
| `e3` | 대기 때문에 늦은 것(처리 ≤ 0.75·T)은 세지 않음, 제출 기준을 최근 처리 p75로 | 34번 다시 열림. 닫힌 직후 요청 자체가 13~23ms |
| `e4` | 반쯤 열림: 열린 동안 시험 요청(결과는 버림, ANE 사용률 20% 이하)으로 깨워 두고 건강할 때만 닫음(평균 ≤ 0.6·T) | 한 번 열린 뒤 닫히지 않음. 시험 요청이 15ms라 기준을 넘지 못함 |
| `e5` | 닫는 기준을 평균 ≤ T·최대 ≤ 2T로 | 사용자 중단 전 276초. 브레이커는 1번만 열렸지만 '시작 못함'이 10,716건 |

`e5`에서 새 결함을 찾았습니다(아직 고치지 않음). **제출 판단에 쓰는 '최근 60건 처리 시간 p75'가 높게 굳습니다.** 느린 결과가 몰린 뒤에는 이 값이 마감 여유보다 커서 요청을 보내지 않고, 보내지 않으니 값이 갱신되지도 않습니다. 고칠 방향은 다음 중 하나입니다.

- 일정 시간 제출이 없으면 시험 요청 하나를 보냅니다.
- 오래된 표본을 버리거나, 시간으로 감쇠시킵니다.
- 예상 처리 시간에 상한을 둡니다.
